# 구현 노트 — 규격 해석 및 가정

규격서(v0.4)가 명시하지 않았거나 해석이 필요했던 부분을 구현이 어떻게 처리하는지 기록한다. 기획 확인 후 달라지면 코드와 이 문서를 함께 고친다.

## 구조

| 영역 | 위치 | 비고 |

| 도메인(순수 함수) | `backend/src/study_invest/{money,params,instruments,event_calendar,pricing,simulator}.py` | DB·프레임워크 의존 없음 |
| 영속·서비스 | `models.py`, `services/*.py` | SQLAlchemy 2.0, PostgreSQL(운영)·SQLite(테스트 기본) |

## 비동기 원칙 (서비스 전체가 멈추지 않게)

`async def` 라우트·의존성은 이벤트 루프 스레드에서 직접 실행된다. 그 안에서 동기 I/O(DB·파일)를 하면 끝날 때까지 **모든 요청이 멈춘다.** 동기 `def`는 FastAPI가 스레드풀에서 실행하므로 여러 요청이 동시에 처리된다.

| 구분 | 방식 | 해당 |
|---|---|---|
| DB·파일을 쓰는 라우트·의존성 | 동기 `def` → 스레드풀 | 거의 모든 라우트, `get_session`, `optional_participant`, `current_params`, 인증 업로드, 이미지 응답 |
| I/O 없는 의존성·라우트 | `async def` → 이벤트 루프에서 즉시 | `get_state`, `get_now`, `bearer_token`, `current_participant`, `require_admin`, `/api/health`, 예외 핸들러 |
| CPU 바운드(수 초) | `async def` + 프로세스 풀 `await` | `/api/admin/simulate` (스레드에서 돌리면 GIL 때문에 다른 요청도 느려짐) |
| 배치 스케줄러 | asyncio 태스크 + `asyncio.to_thread` | `_scheduler` → `run_due` |

- **회귀 방지**: `install_event_loop_guard`가 이벤트 루프 스레드에서 실행되는 SQL을 감지한다. 테스트는 `raise`(해당 테스트 실패), 운영 기본값은 `warn`(로그). `tests/test_async_policy.py`는 async 라우트·의존성 허용 목록을 고정하고, 업로드가 스레드풀에서 돌며 시뮬레이션 중에도 `/api/health`가 응답하는지 확인한다.
- **풀 크기**: 스레드풀 40(`STUDY_INVEST_THREADPOOL_SIZE`), api 연결 풀 20(대기 10초 넘으면 503), 배치 전용 풀 2. 풀 설계와 연결 예산은 [db-pools.md](db-pools.md).
- **워커 수**: 앱 내 스케줄러는 프로세스마다 돈다. `uvicorn --workers N`이나 레플리카를 늘리면 스케줄러는 한 곳에서만 켜고(`STUDY_INVEST_SCHEDULER=1`), 나머지는 끈다. 여러 개가 동시에 돌아도 DB 제약으로 중복 공시·정산·지급은 막히지만 오류 로그가 남는다.

## 동시성 (PostgreSQL 기준)

| 상황 | 처리 |
|---|---|
| 같은 참가자의 현금·보유 변경(주문·보상) | 모두 `lock_participant`를 거친다: 참가자 행과 보유 행을 `FOR UPDATE`로 잠그고 **다시 읽는다**(세션에 있던 옛 값도 덮어씀). 요청 초반에 읽은 현금·보유는 쓰지 않는다. |
| 18:00 경계의 주문 vs 정산 | 주문은 운영일 행에 `FOR SHARE`, 정산은 `FOR UPDATE`. 정산은 진행 중인 주문이 끝난 뒤 집계하고, 정산 이후 주문은 `MARKET_CLOSED`. |
| 배치 중복(워커·레플리카·수동 실행) | 공시·정산·수동 가격은 `pg_advisory_xact_lock`으로 직렬화. 스케줄러는 `try` 잠금이라 다른 곳이 실행 중이면 조용히 건너뛴다. |
| 인증 코드 동시 요청 | 재요청 대기·하루 한도 검사와 발급을 `pg_advisory_xact_lock`(`CODE_LOCK_KEY`)으로 직렬화. 메일 발송 전 커밋에서 풀린다. |
| 파라미터 폼 저장 vs '인증된 참가자만 거래' 스위치 | 둘 다 읽기 전에 `params_lock`(advisory lock)을 잡아 서로 덮어쓰지 않는다. |
| 비밀번호 재설정 vs 옛 비밀번호 로그인 | 로그인은 토큰을 만들기 전 참가자 행을 `FOR SHARE`로 다시 읽어 해시를 확인, 재설정은 UPDATE를 먼저 보내고 토큰을 지운다. |
| 동시 중복 인증·등록 | 세이브포인트로 유니크 제약 위반을 잡아 409(`ALREADY_CERTIFIED`·`IDENTITY_TAKEN`·`NICKNAME_TAKEN`). 그 밖의 무결성 충돌도 전역 핸들러가 409 `CONFLICT`. |
| 전일 정산이 계속 실패 | 09:00 공시는 그대로 진행해 전일 가격을 이월한다(오늘 장은 열림). 이월 뒤에는 전일 정산을 다시 돌리지 않는다. |
| 큰 요청 본문 | ASGI 미들웨어가 `Content-Length`로 먼저 거부하고, 길이 없는 스트림은 받는 도중 한도 초과 시 413. 업로드 경로는 사진 한도 + 64KiB, 나머지는 1MiB. |
| 스케줄러 지연 | 30초 주기와 별개로 09:00·18:00 정각 직후 깨어난다. |

SQLite(테스트 기본)는 행 잠금이 없으므로 동시성 테스트(`tests/test_concurrency.py`)는 PostgreSQL에서만 돈다.

## 수치 한계

모든 가격·수량·금액이 DB의 BIGINT와 정수 연산 범위 안에 머물도록 한 곳(`params.py`)에서 정한다.

| 한계 | 값 | 적용 |
|---|---|---|
| `PRICE_MAX` | 10억 원 | 가격 산정 결과(코인·주식 모두 클램프), 수동 개입가, 가격 파라미터 |
| `QUANTITY_MAX` | 10억 | 주문 수량 |
| `REWARD_CASH_MAX` | 1억 원 | 인증 1건당 보상 현금(`reward_cash`) |
| `AMOUNT_MAX` | 10^15원 | 가상 유동성 등 금액 파라미터 |
| `COIN_CAP_MAX` | 10.0(+1000%) | 코인 일일 상승 상한·안정기 상한 파라미터 |
| `CALM_ROUNDS_MAX` | 100 | 코인 초반 안정기 회차 수 파라미터 |

한 주문 금액은 최대 `PRICE_MAX × QUANTITY_MAX = 10^18`로 BIGINT(약 9.2×10^18) 안이다. 보상을 매일 상한까지 받아 최저가(10원) 종목에 넣고 그 종목이 `PRICE_MAX`까지 올라도 평가금액은 약 10^17원이다. 실수 파라미터는 NaN·Infinity를 거부한다.

## 해석·가정

### 장 운영·체결

- **주문 접수 시간**은 KST `[09:00, 18:00)`이다. 18:00:00 주문은 마감으로 거부한다.
- **시작가 공시 전 주문**(09:00 배치가 아직 안 돈 경우)은 `MARKET_NOT_OPENED`로 거부한다. 정산이 끝난 날의 주문은 `MARKET_CLOSED`.
- **거부된 주문도 기록**한다(F-09). 사유 코드와 한국어 메시지를 함께 돌려준다.
- **1일 1종목 매수 상한**은 코인을 포함한 5종목 모두에 적용한다. 당일 체결된 **매수 금액 누적**으로 판단하므로, 매도 후 재매수해도 한도가 늘지 않는다. 한도 = `floor(총자산 × 0.4)`이며, 장중 가격이 고정이고 수수료가 없으므로 총자산은 장중에 변하지 않는다.
- **평균단가**: 매수 시 매입금액을 더하고, 매도 시 평균단가를 유지하도록 매입금액을 비례 차감(원 단위 반올림)한다.
- **수량 범위**: API는 저장 가능한 값(64비트 정수)만 받는다(밖이면 422). 그 안에서 1~10억이 아닌 수량은 `INVALID_QUANTITY` 거부 주문으로 기록한다.

### 가격·정산

- **반올림**: 10원 단위 사사오입(0.5는 올림). 파이썬 `round()`(은행가 반올림)는 쓰지 않는다. 주식 계산은 유리수(`Fraction`)로 정확히 한다.
- **주식 기준선**은 주식 종목 수(4)로 나눈다. 매수 집계 `Bᵢ`는 **체결된 매수만**이다(매도 미포함).
- **코인 표시 상한 5,000,000원**은 가격 자체에 적용하는 클램프다(파라미터 `coin_price_cap`, `null`이면 해제). 코인 최저가는 규격에 없으나 0원 방지를 위해 10원을 보장한다.
- **정산 가능 조건**: 해당일이 공시됐고, 18:00 이후이며, 다음 운영일이 아직 공시되지 않았어야 한다. 마지막 운영일(10-16)은 반영일이 없어 정산하지 않는다(`NO_ROUND`).
- **배치 실패**: 정산은 한 트랜잭션이라 실패 시 아무것도 기록되지 않는다. 다음 날 09:00까지 재실행되지 않으면 공시 배치가 **전일 가격을 그대로 이월**(`source=carry_over`)한다. 이월 후에는 전일 정산을 다시 돌릴 수 없다(장중 가격 불변 보장).
- **가격 이력 공개 시점**: 정산(18:00)이 다음 날 가격을 확정해 기록하지만, 시세 API는 **공시(09:00)된 운영일만** 보여준다.
- **수동 가격 개입**(F-11): 아직 공시되지 않은 운영일에만 가능하며, 정산 결과보다 우선한다(정산이 덮어쓰지 않음). 10원 단위 양수만 허용.
- **전일 대비 기준**: 공시(09:00) 때 "그 전에 공시된 마지막 시작가"로 확정한다. 며칠 앞서 넣은 수동 개입가도 그사이 정산된 가격 기준으로 변동률이 계산된다.
- **가격 파라미터**: `stock_min_price`, `coin_price_cap`은 10원 단위만 허용한다(모든 가격이 10원 단위를 유지).
- **정산 난수**: 운영은 `random.SystemRandom`. 추출한 `p`, `X`를 정산 로그에 남긴다.
- **코인 초반 안정기**(v0.4): 정산 회차가 1~`coin_calm_rounds`(기본 3)이면 상·하한만 `coin_calm_cap`·`coin_calm_floor`(+30%·-10%)로 바꿔 추출하고, 정산 로그 `coin.calm`에 남긴다. 회차는 날짜로 정해지므로(`round_of`) 중간 정산이 실패해 가격이 이월돼도 안정기가 뒤로 밀리지 않는다. 안정기 상·하한은 평소 상·하한과 따로 검사한다(저장된 값이 엇갈려도 파라미터를 읽지 못해 배치가 멈추지 않게). 참가자 화면은 `GET /api/event`의 `coin`(평소·안정기 범위, 안정기 마지막 반영일)으로 안내한다.
- **코인 평소 범위**(v0.4, 2026-10-04 갱신): v0.4는 기본 상·하한을 +200%·-40%(상승폭 지수 3)로 낮춰 20배 초과 확률을 약 0.45%로 만들었다. 이후 기본값을 상승폭 지수 2, 상한 +80%로 바꿨다. 20배 초과 확률은 0.00%지만 로그 기대값이 약 -0.042, 누적 중앙값이 약 0.74배라 SPEC-COIN-5는 충족하지 못한다(SPEC-COIN-7은 충족). `tests/test_simulator.py`는 v0.4 값을 `V04`로 고정해 검증한다.
- **파라미터 기본값과 저장값**: 기본값은 저장된 파라미터(`params_records`)에 그 키가 없을 때만 쓰인다. 관리자 화면에서 파라미터를 저장한 적이 있는 서버는 코인 상·하한 같은 기본값 변경이 자동으로 반영되지 않으므로 관리자 화면에서 직접 바꾼다. 새로 생긴 키(`reward_cash`, `coin_calm_*`)는 저장값에 없으므로 기본값이 쓰인다.
- **시뮬레이터**(F-13): 실제 정산과 같은 `draw_coin`·`is_calm_round`로 경로를 만든다. 일일 통계는 평소 회차(`daily`)와 안정기 회차(`calm_daily`)를 따로 내고, 누적 배수는 안정기를 포함한 전체 경로로 낸다.

### 공부 인증·보상

- **마감 시각**은 해당 분(分)까지 포함한다. 마감 23:59이면 23:59:59 제출도 당일로 집계한다.
- **1인 1일 1회**는 상태와 무관하다. 반려된 날짜도 다시 제출할 수 없다. 화면은 `GET /api/me/certification-status`(제출 API와 같은 함수 `submission_status`)만 보고 업로드 가능 여부를 정한다.
- **이미지 해시 중복**(SHA-256)은 자동 반려하지 않고 `duplicate_of`로 표시해 검수자가 판단한다. 형식은 매직 바이트로 확인한다(JPEG·PNG·WEBP·HEIC, 10MB 이하).
- **이벤트 기간 밖 날짜**로 집계되는 제출(시작 전, 마지막 날 마감 이후)은 거부한다.
- **보상**(v0.4): 승인분 중 미지급·대상일 < 공시일인 인증을 09:00 공시 때 한꺼번에 지급한다. 지급 시점 파라미터의 현금 `reward_cash`원(기본 250,000원)을 현금잔고에 더하고 인증 행 `reward_cash`에 기록한다. 주문과 같은 참가자 잠금(`lock_participant`)을 거쳐 최신 현금에 더한다. 마지막 날 인증분은 지급일이 없다. v0.3에 병더리움으로 지급된 기록(테스트 서버)은 마이그레이션 후 `reward_cash`가 비어 있고, 받은 코인은 보유에 그대로 남는다(수익률에서는 이익으로 잡힌다).
- **반려 반복 → 경고 → 실격**의 기준 횟수는 규격에 없어 **관리자가 수동으로** 상태를 바꾼다. 관리자 참가자 목록에 반려 횟수를 보여준다.
- **실격**: 주문·인증 제출 불가, 보상 미지급, 랭킹 제외.
- **개인정보**: `study-invest purge-images`가 이벤트 종료 후 업로드 디렉터리의 인증 사진 파일을 **전부** 지운다(DB에 없는 파일 포함, 해시는 감사용으로 보존). 종료 후 30일 안에 실행해야 한다.
- **사진 파일과 트랜잭션**: 사진은 트랜잭션에 묶어 저장한다(`track_new_file`). 커밋되지 않고 끝나면(롤백·예외·커밋 없이 종료) 파일도 지운다.

### 참가자·랭킹

- **1인 1계정 = 학교 메일 + 학번**(06-abuse-risk §2): 가입 때 학교 메일·이름·학번·학과를 받는다. 학번(숫자 10자리)도 유니크라 한 학번에 한 계정이다. 메일은 `@skku.edu`·`@g.skku.edu`만 받고, 같은 ID의 두 도메인은 한 사람이라 `ID@g.skku.edu`로 합쳐 `participants.email`(유니크)에 저장한다(`normalize.parse_school_email`). `+` 별칭은 거부한다(같은 메일함으로 배달되어 계정을 여러 개 만들 수 있다). Google Workspace는 ID의 마침표를 무시하지 않으므로 마침표는 그대로 둔다. 동시 가입은 유니크 제약으로 판정한다(두 도메인으로 동시에 가입해도 하나만 된다).
- **인증 코드**(`services/email_verification.py`, `email_verifications` 테이블): 6자리, SHA-256 해시로만 저장, 10분 유효, 메일마다 최신 코드만 유효, 5번 틀리면 무효. 재요청 60초, 메일당 24시간 5통, 전체 24시간 `STUDY_INVEST_MAIL_DAILY_LIMIT`통(기본 400, 발송 계정 한도 보호). 로그인한 요청(`/api/me/email/code`)은 계정마다도 60초·5통을 센다(`email_verifications.requested_by`): 주소를 바꿔 가며 남의 메일함에 뿌리거나 전체 한도를 혼자 소진하지 못하게. 화면의 카운트다운은 편의일 뿐 제한은 서버가 건다(주소를 고치면 화면 카운트다운은 초기화). 틀린 횟수는 요청이 실패해도 커밋한다(`api/email_codes.py`). 링크 대신 코드를 쓰는 이유: 학교 메일 보안 필터가 링크를 미리 열어 1회용 링크를 써 버릴 수 있다. 유효시간·재요청 간격은 **실제 시각**을 쓴다(테스트 시계 배속을 따르면 10분이 25초가 된다).
- **메일 발송**(`mail.py`): SMTP(`STUDY_INVEST_SMTP_*`). 코드를 저장하고 **커밋한 뒤**(DB 연결·발급 잠금을 돌려준 뒤) 보낸다. SMTP를 기다리는 동안 api 풀을 잡지 않는다(테스트로 고정). 느린 SMTP가 공용 스레드풀(기본 40)을 다 차지하지 않게 동시 발송은 `MAIL_CONCURRENCY`(8)건까지이고, 꽉 차면 코드를 만들기 전에 503 `MAIL_BUSY`. 발송에 실패해도 코드 기록은 지우지 않는다: 재요청 대기·한도에 계속 세고(SMTP 장애 중 무한 재시도 방지), 연결 종료 중 오류처럼 메일이 실제로 갔을 수도 있어 코드도 유효하다. `STUDY_INVEST_SMTP_HOST`가 비면 **fail closed**: 코드를 로그로 흘리지 않고, 코드를 만들기 전에 503 `MAIL_NOT_CONFIGURED`로 거절한다(앱은 뜨고 코드 없는 가입·로그인은 된다). 로컬 개발·CI만 `STUDY_INVEST_MAIL_LOG_ONLY=1`로 메일 내용을 로그에 남긴다.
- **이벤트 종료 후 인증 금지**: 종료 후에는 학교 메일 인증(`/api/me/email/code`·`/api/me/email`)을 409 `EVENT_ENDED`로 거절한다. `purge-personal-info`로 지운 뒤 미인증 계정이 메일·학번을 다시 등록해 개인정보가 재수집되지 않게 한다(가입도 이미 막혀 있다).
- **보내는 주소와 1인 1계정 키**: 1인 1계정 키(`email`, `ID@g.skku.edu`)와 코드를 보내는 주소(`email_address`, 입력한 도메인 그대로)를 따로 둔다. skku.edu와 g.skku.edu는 같은 ID여도 메일함이 다를 수 있다.
- **본인 응답의 메일**: `/api/me`·로그인 응답에는 가린 주소(`masked_email`, `k***@skku.edu`)만 싣는다. 화면은 주소를 넘기지 않고 "등록한 메일로 코드 받기"(`POST /api/me/email/code`)를 쓰고, 서버가 등록 주소로 보낸다. 전체 주소는 관리자 응답에만 있다.
- **인증은 선택, 거래 제한은 관리자 스위치**: 기본(`STUDY_INVEST_EMAIL_VERIFICATION=0`)은 가입 때 코드 없이 메일 주소만 받아 **미인증**으로 가입시킨다(코드를 함께 내면 인증된 채로 가입). 미인증 참가자도 평소에는 모든 기능을 쓴다. 이벤트 중 부정 행위가 보이면 관리자가 참가자 탭에서 **'인증된 참가자만 거래'**(`EventParams.verified_only_trading`, `PUT /api/admin/trading-access`)를 켠다. 그동안 미인증 참가자의 **주문만** 403 `VERIFICATION_REQUIRED`(조회·공부 인증 제출은 그대로)이고, 화면 위에 인증 안내가 뜬다. 스위치는 파라미터에 저장해 이력·감사 로그에 남고, 파라미터 폼 저장(`PUT /api/admin/params`)은 이 값을 보내지 않으면 그대로 둔다. 두 저장은 파라미터를 읽기 전에 advisory lock(`params_lock`)을 잡아, 동시에 와도 서로 읽은 옛 값으로 상대 변경을 덮어쓰지 않는다.
- **인증 방법**(`participants.verified_at`·`verified_via`): ① 참가자가 등록한 메일로 코드를 받아 코드만 입력(`POST /api/me/email/code` → `/api/me/email`, `verified_via=email`). 등록 메일을 잘못 적었으면 다른 주소로 받아 인증하고, 그 주소가 등록 메일이 된다. 미인증 계정이 쓰는 메일에는 코드를 보내 주지만, 그 메일로 다른 사람이 가입·인증할 수는 없다. **메일 코드로 인증된 계정은 메일을 바꿀 수 없다**(이미 본인 것으로 확인됨, 세션 탈취 → 메일 변경 → 재설정 경로 차단). 관리자 인증만 받은 계정은 메일을 확인하지 않았으므로 계속 메일 인증으로 바로잡을 수 있다. ② 관리자가 학번·이름·학과를 보고 참가자 탭에서 인증 처리·취소(`verified_via=admin`, 감사 로그 `participant.verify`·`unverify`). 메일 인증 도입 전 계정(`needs_profile`)은 ①에서 이름·학번·학과·동의도 함께 받는다. `STUDY_INVEST_EMAIL_VERIFICATION=1`이면 가입 때 코드가 필수다.
- **비밀번호 재설정**: 학번(학교 메일도 받음)을 입력하면 그 계정의 등록 메일(인증 여부와 상관없이)로만 재설정 코드(`purpose=reset_password`)를 보낸다. 다른 주소로는 받을 수 없다(남의 학번만 알아도 계정을 가져가는 경로 차단). 응답에는 가린 주소만. 학번으로 가입 여부와 가린 메일을 알 수 있지만, 가입 때도 학번 중복을 알려 주므로 새로 드러나는 것은 작다. 바꾸면 그 계정의 다른 로그인(토큰)은 모두 끊는다: 로그인은 비밀번호 확인(scrypt) 뒤 참가자 행을 공유 잠금(`FOR SHARE`)으로 다시 읽어 해시가 그대로일 때만 토큰을 만들고, 재설정은 해시 UPDATE를 먼저 flush해 그 잠금을 기다린 뒤 토큰을 지운다. 그래서 재설정과 동시에 옛 비밀번호로 한 로그인도 살아남지 않는다(PostgreSQL 동시성 테스트). 가입·인증 코드와 재설정 코드는 서로 바꿔 쓸 수 없고, 재요청 대기·하루 한도는 용도와 상관없이 메일마다 센다.
- **개인정보**: 가입 때 수집·이용 동의(항목: 학교 메일·이름·학번·학과, 목적, 보유 기간, 거부 권리)를 받는다(`privacy_consent`). 이름·학번·학과는 관리자 화면에만 보인다. 감사 로그에는 메일·학번을 남기지 않는다. 이벤트가 끝나면 `study-invest purge-personal-info`로 메일·이름·학번·학과와 코드 기록을 지운다(인증 시각은 남긴다).
- **식별자·닉네임 정규화**: 입력을 NFKC·대소문자 무시·앞뒤 공백 제거로 정규화한 **뒤** 길이를 검사한다(`normalize.py`). 닉네임은 NFC·공백 제거 뒤 2~20자.
- **401 처리(프론트엔드)**: 요청마다 보낸 토큰·관리자 키를 기억하고, 401은 그것이 아직 현재 값일 때만 세션 거절로 본다. 로그아웃→로그인 사이에 늦게 도착한 이전 세션의 401이 새 세션을 끝내지 않는다.
- **쉬운 비밀번호 거부**: 가입·비밀번호 재설정 때 [zxcvbn](https://github.com/dwolfhub/zxcvbn-python)으로 점수를 매겨 2 미만(0~4)이면 422 `WEAK_PASSWORD`(`services/auth.ensure_strong_password`). 그 사람의 학번·이름·닉네임·메일(과 아이디 부분)을 `user_inputs`로 넘겨 이것이 들어간 비밀번호도 쉬운 것으로 본다. 긴 입력에서 느려지지 않게 앞 100자만 본다. 판단은 서버만 한다(프론트엔드용 사전은 번들이 커서 넣지 않음). 검사 도입 전 비밀번호로의 로그인은 막지 않는다.
- **로그인**: 학번 + 비밀번호(scrypt) + Bearer 토큰. 학교 메일(두 도메인 어느 쪽이든)이나 메일 인증 도입 전 식별자도 받는다. 맞는 계정을 학번 → 메일 → 예전 식별자 순으로 찾아 비밀번호가 맞는 첫 계정으로 로그인한다(예전 식별자가 다른 사람의 학번과 같은 숫자여도 각자 로그인된다).
- **닉네임**은 유일하다(랭킹 공개명).
- **참가 신청**은 이벤트 종료일까지 받는다(중도 참가 허용, 시드 동일).
- **랭킹**: 총자산 100%, 동점은 공동 순위(1, 2, 2, 4). 인증 연속일수는 오늘 승인분이 없으면 어제부터 센다.
- **수익률**(v0.4): (총자산 − 투입 원금) ÷ 투입 원금, 투입 원금 = 시드 + 받은 인증 보상 합계(`certifications.reward_cash`의 합, `services.common.Valuation`). 포트폴리오·랭킹·관리자 참가자 목록이 같은 계산을 쓴다. 단순 수익률이라 받은 보상을 투자하지 않고 두면 수익률이 0%에 가까워진다(시간가중 수익률 아님). 순위와 동점 비교는 유리수로 정확히 한다.
- **수익률 순위**: 랭킹(실격자 제외)의 `return_rank`는 수익률 높은 순 공동 순위다. 화면은 총자산 순과 수익률 순을 전환해 보여 준다.
- **관리자 인증**: `X-Admin-Key` 헤더(환경 변수 `STUDY_INVEST_ADMIN_KEY`). 비어 있으면 관리자 API가 모두 막힌다.
